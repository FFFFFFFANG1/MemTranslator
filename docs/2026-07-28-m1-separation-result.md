+ 60 个 dilution probe，零 judge，全部机械子串判定。

## 三条结论，两条是坏消息

### 1. 生命周期能测，检索不能测

suite 分得开「有失效逻辑」和「没有」：real / recency-32 的 SUPPRESS 是 1.00，
null-dump 是 0.57，差 **0.43**。死条目一旦进了 prompt，有 **0.85** 的概率被带进改写——
陷阱是有效的，不是摆设。

suite 分不开「聪明的检索」和「取最新 32 条」：real 与 recency-32 的 SUPPRESS 差
**恰好 0.00**。两者都靠 `status` 过滤挡住死条目，而 `recall()` 多做的那两件事
（scope 过滤、key 排序）在这套判据上一分钱都没换到。

预注册门槛写的就是 real vs recency-32，所以判 FAIL。这不是门槛定错了——
它精确地问出了「480 条语料能不能买到区分度」，答案是买不到。

### 2. `_scope_ok` 的观测贡献是零，而且这次是直接测出来的

recency-32 不做 scope 过滤，所以越界规则 **60/60 全部进了 prompt**，
而它被带进改写 **0/60**。翻译器自己按话题判断就把越界规则挡掉了，
`_scope_ok` 没有产生任何可观测的行为差异。

这与 `translate._requirement_block` 只打印 `- [id] text`、scope 字段从不进 prompt
是同一件事的两端：产品既没有把 scope 告诉模型，也不需要——模型自己会过滤。
**scope 维度应当整个退出计分**，或者先改产品（scope 进 prompt）再谈测它。

### 3. CARRY 有稀释效应，之前那条"CARRY 不敏感"是小样本假象

| 注入条数 | CARRY |
|---|---|
| 5.7 | 0.70 |
| 27.7 | 0.63 |
| 32.0 | 0.50 |

n=60/格，单调下降 20 个点。对抗复核当时测的是 6/6、5/6、5/6（n=6），据此判定
"CARRY 对注入集合几乎不敏感"，并把 headline 权重从 0.6 压到 0.25。**这个依据不成立**，
权重决定要重做。

（注意 null-dump 的 CARRY=0.00 是构造产物不是发现：它取插入序的头 32 条，而 live 规则
按构造是最新的，所以它结构上不可能带上——这个臂只有死条目那一列有意义。）

## 顺带打掉方案里的一根承重柱：distinctive 码活不过改写

第一版 M1 用发明的编码当标记（`QX-4417`），CARRY 全线 0.00。实际输出：

```
注入：邮件结尾另起一行写备案号 QX-4417
改写：给供应商写封邮件催一下上个月的发票。邮件正文开头标注版本号，邮件结尾另起一行写备案号。
```

规则带过去了，编码被规范化掉了。合成方案把 gate 压在 `E-mech` band
（权重 0.50，卖点是"全部零 judge 在环、`not_contains(distinctive)`"）——
**这个 band 建在一个不成立的前提上**。

改法已落进实验代码并有效：不用编码，用**语义对立的前后继对**，对比词是规则内容的一部分
（座机↔手机号、版权声明↔作者、三级↔一级），改写时会被带过去。副作用是"推翻"必须改变
规则内容，这本来也更真实——只换个编码的 supersede 是假的。

## 该怎么改计划

1. **语料缩量，重心从广度移到失效。** 唯一实测有区分度的资源是失效事件与死条目 probe
   （0.43 的臂间差全部来自这里）。480 条铺 12 个 episode 的宽度买不到东西。
2. **scope 退出计分**，降为观测；或者先修产品（scope 进 prompt）再重跑本实验。
3. **CARRY 权重重议**，0.25 的依据（n=6）已被 n=60 推翻。
4. **`E-mech` band 重新定义**：distinctive 码不可用，机械判据只能建在语义对立对上，
   这限制了哪些 constraint 可以进 mech band——不是所有规则都有天然的对立面。
5. 重跑门槛：修产品之后，`real - recency-32` 的差应当来自 scope 过滤真正生效。
   在那之前，Suite E 能诚实声称的只有一句：**被撤回的规则会不会停止生效**。

## 复现

# 续：aged 布局，以及 BM25 的效果（同日）

## 我上一轮的实验设计有问题

第一轮把 live 规则放在 store 的**最新**位置。recency-32 取最新 32 条，所以它永远保得住
live 规则——**排序算法没有任何可以证明的东西**。测出 +0.00 的差有一半是构造出来的，
不全是产品的问题。

加了 `--layout aged`：live 规则埋到最老，被 49 条更新的 filler 压着。这时 tail-取 cap 会
把它丢掉，只有理解查询的排序器能把它捞回来。这才是检索质量所在的位置。

## aged 布局，改 BM25 之前（`M1-aged-20260728-114215.json`）

| 臂 | CARRY | SUPPRESS |
|---|---|---|
| real | 0.45 | 1.00 |
| recency-32 | **0.00** | 1.00 |
| null-dump | 0.72 | 0.97 |
| flat-dump | 0.88 | 1.00 |

real 0.45 vs recency-32 0.00——**排序是有价值的，第一轮只是没给它测的机会**。
逐 facet 看，价值完全取决于 `_KEY_LEXICON` 的 14 个词根碰巧覆没覆盖到查询词：

| facet | real CARRY [注入率] | 原因 |
|---|---|---|
| email | 1.00 [1.00] | 词表 `email` 含「邮件」，每条请求都有 |
| code | 0.35 [0.35] | 部分请求说「代码」 |
| doc | **0.00 [0.00]** | key 是 `report.format`，词表给 报告/周报/格式，请求说「文档」 |

## 换 BM25 之后（`M1-aged-20260728-115029.json`）

`recall()` 超过 cap 时改用 BM25 打分（`src/memtranslator/bm25.py`，零依赖，
CJK 字符二元组 + Latin 词元，不需要任何词表）。同一布局、同一批 probe：

| facet | 词表 → BM25（CARRY [注入率]） |
|---|---|
| email.signoff | 1.00 [1.00] → 1.00 [1.00] |
| code.header | 0.35 [0.35] → 0.45 [0.45] |
| doc.toc | **0.00 [0.00] → 0.65 [0.70]** |
| **real 总计 CARRY** | **0.45 → 0.70** |

**注入率是确定性的**（只取决于选择器，不经过 LLM），所以 doc 那一格 0.00 → 0.70 是干净证据，
没有采样噪声。real 与 recency-32 的 CARRY 差现在是 **0.70**。

不用 `recall()` 的两个臂（null-dump、flat-dump）也动了（0.72→0.33、0.88→0.68），
它们的选择逻辑没变，动的是 prompt（scope 现在会打印）加 run 间方差。
这部分不归 BM25，也不该算进 BM25 的功劳。

## 对预注册判决的处置

**两个门槛按原文判仍然是 FAIL，我不追认成 PASS。** 但 FAIL 的原因现在清楚了，是**指标选错**：

- 检索质量体现在 CARRY 上，我把门槛写在了 SUPPRESS 上。SUPPRESS 差 +0.00 在两个布局里
  都成立，因为 real 和 recency-32 都靠 `status` 挡死条目，谁也不比谁强——这一项本来就
  测不出排序。
- 生命周期体现在「后继缺席时」。fresh 布局死条目泄漏 0.85、aged 只有 0.05，差别在于
  aged 让 live 和 dead 同时进 prompt，两者内容对立，模型 95% 选了新的。
  **翻译器在能看见前后继时自己就把 supersede 解对了**——这是产品的好消息，
  同时说明陷阱只在后继被 cap 砍掉时才咬得住。

下一版门槛应当写成：aged 布局下 real 与 recency-32 的 **CARRY** 差 ≥ 0.30，
且 fresh 布局下死条目泄漏 ≥ 0.60。这两条现在分别是 0.70 和 0.85，都过。
但这是**事后**校准出来的门槛，只能用于下一次改动的对照，不能拿来宣称这一次通过了。
