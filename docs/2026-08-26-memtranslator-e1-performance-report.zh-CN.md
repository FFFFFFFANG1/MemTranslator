# MemTranslator E1 含噪声场景性能报告

[原文](2026-08-26-memtranslator-e1-performance-report.md) | **简体中文**

**报告日期：** 2026-08-26  
**评测对象：** MemTranslator 原生端到端流水线  
**对照对象：** Codex 文件记忆（`AGENTS.md + MEMORY.md`，GPT-5.5 medium）  
**数据集：** E1 协议 v3，12 个 `episodes-noisy` 交互序列

## 摘要

MemTranslator 在 E1 含噪声场景中的当前表现是：**适用记忆能较稳定地带入当前任务，失效或越界记忆多数能被抑制，但写入后的内部状态仍有明显误差。** 按 E1 的正式口径，CARRY、SUPPRESS、STATE 三个评分维度分别报告，不存在官方加权总分。

| 指标 | MemTranslator | 95% 置信区间 / 计数 | 含义 |
| --- | ---: | ---: | --- |
| CARRY 宏平均 | **0.713** | `[0.637, 0.794]` | 适用记忆按交互序列计算的宏平均命中率 |
| CARRY 微平均 | **69.2%** | `74/107` | 107 个应带入的记忆中命中 74 个 |
| SUPPRESS 宏平均 | **0.894** | `[0.788, 0.970]` | 不适用记忆按交互序列计算的宏平均抑制率 |
| SUPPRESS 微平均 | **85.7%** | `30/35` | 35 个机械评分负例中抑制 30 个，泄漏 5 个 |
| STATE 宏平均 | **0.707** | `[0.671, 0.738]` | 记忆库与标准答案中生命周期状态的对齐程度 |
| STATE 微平均 | **70.6%** | `1861/2637` | 合并所有检查点状态判定后的命中率 |
| Task-perfect（任务全部正确） | **66.0%** | `68/103` | 103 个计分任务中，68 个同时满足全部正负要求 |

与 Codex 文件记忆相比，MemTranslator 的 CARRY 观测值更高，Codex 的 SUPPRESS 观测值更高：

- MemTranslator 多命中 **5/107** 个适用记忆，CARRY 宏平均高 **0.041**。
- Codex 多抑制 **4/35** 个负例，SUPPRESS 宏平均高 **0.093**。
- Task-perfect 为 **68/103 vs 67/103**，只差 1 个任务，实际表现接近。
- 按交互序列配对的自助法重采样中，CARRY 与 SUPPRESS 的差值区间都跨过 0；这轮结果支持“双方强项不同”，**不支持任何一方总体显著优于另一方**。

## 1. E1 测什么

E1 是一套完整的记忆生命周期测试，不只是对 Translator 模型的单点测试。
它覆盖用户历史进入系统后的提取、写入、失效、检索和最终请求改写。
因此，本报告中的“MemTranslator E1 分数”应理解为**原生完整系统效果**。

三个评分维度的含义如下：

- **CARRY**：当前任务应该应用的 `should_apply` 记忆，是否被明确写入最终请求。规则原文或预先编写的等义改写精确出现时，走机械判定的快速路径，其余由只回答是或否的专用评判器判定。仅仅“输出碰巧兼容该偏好”，但请求中没有对应要求，不算命中。
- **SUPPRESS**：`must_not_apply` 记忆中用于识别该规则的独特文本是否没有出现在最终请求中。它覆盖已失效、作用域不匹配等不应生效的规则，完全采用机械评分，不使用 LLM 评判器。
- **STATE**：内部记忆库是否正确表达标准答案中的生命周期状态。活跃记忆应存在有效对齐项，失效记忆不应仍有活跃对齐项；先做子串对齐，未命中时再交给专用评判器。

另外，**Task-perfect** 要求一个任务上的所有 CARRY 和 SUPPRESS 目标同时正确；它比单条记忆命中更严格。

## 2. 测试规模与配置

含噪声语料在每两个预先编写的轮次之间，固定插入 5–10 条 OASST1 普通根提示词，
保留原始探针、生命周期和检查点的语义，只重新映射序列编号。
它用于模拟长期历史中“真正需要记忆的偏好被大量普通对话稀释”的情况。

| 项目 | 数值 |
| --- | ---: |
| 交互序列 | 12 |
| 预先编写的轮次 | 744 |
| 噪声轮次 | 5,481 |
| 扩展后总轮次 | 6,225 |
| 探针 / 检查点 | 209 |
| 计分任务 | 103 |
| 标准要求 | 467 |
| CARRY 目标 | 107 |
| SUPPRESS 目标 | 35 |

本轮 MemTranslator 使用原生提取、Store、BGE-M3 检索和 DeepSeek V4 Flash Translator；作用域召回上限为 16。
结果快照的指标版本为 12，协议版本为 3；CARRY 评判器为 GLM-5.3，STATE 未命中项的评判器为 DeepSeek V4 Pro。
12 个交互序列均完整结束，CARRY 评判器解析异常标记为 0。

### 3.1 适用记忆：有效，但仍是主要损失来源

CARRY 宏平均为 0.713，微平均为 74/107。这说明 MemTranslator 已能在大量噪声与 29–42 条峰值活跃记忆下保住约七成适用偏好，但仍漏掉 31 个应带入项。

逐序列表现并不均匀：`e-03` 达到 1.000，`e-02`、`e-07`、`e-12` 达到 0.800；`e-01`、`e-04`、`e-09` 只有 0.500–0.545。当前读取路径并未全面失效，但对交互序列、用户设定和记忆组成较敏感。

### 3.2 失效记忆：总体较强，错误集中在少数交互序列

SUPPRESS 宏平均为 0.894，微平均为 30/35。12 个交互序列中，8 个有负例的序列达到 1.000；5 次泄漏全部集中在：

- `e-01`：4/6，泄漏 2 个；
- `e-04`：4/6，泄漏 2 个；
- `e-06`：1/2，泄漏 1 个。

因此，SUPPRESS 的整体表现是大部分场景全部正确，少数生命周期较复杂的交互序列明显掉分。

### 3.3 记忆库状态：约七成正确，仍有明确改进空间

STATE 宏平均为 0.707，微平均为 1861/2637。最低为 `e-03` 的 0.563，最高为 `e-05` 的 0.796。
`e-03` 同时取得 CARRY 1.000，说明检查点上的记忆库全局状态质量与当前探针的可用输出相关，但并不等价。
不能用 CARRY 替代 STATE，也不能仅凭 STATE 推断每个任务一定失败。

### 3.4 端到端任务成功率

68/103 个任务做到所有正负要求同时正确，Task-perfect 为 66.0%。这个数字与 CARRY 微平均接近，但更严格：只要一个任务中漏掉任意适用记忆，或泄漏任意不适用记忆，整题就不算全部正确。

## 4. 与 Codex 文件记忆的对比

### 4.1 对照协议

Codex 基线在相同的 12 个 E1 含噪声交互序列上维护 `AGENTS.md + MEMORY.md`：
每个预先编写的探针前增量更新文件；在有 CARRY/SUPPRESS 目标的探针上，
使用冻结的文件和当前请求，发起一次独立的 GPT-5.5 medium 改写调用。
两边复用相同的 E1 CARRY 评判器和机械 SUPPRESS 评分器，标准答案不进入被测系统调用。

这使语料和评分器可比，但它仍然是**系统级比较**，不是单组件 A/B 测试：
两边的记忆表示、写入器、检索、读出模型和维护协议都不同。

### 4.3 按交互序列配对分析

当前仓库保留了 MemTranslator 的逐序列机器结果，用户提供的 Codex 报告也给出了逐序列表，因此可以按序列配对计算差值。
使用 2,000 次重采样、随机种子 17，进行按交互序列簇配对的自助法分析：

| 配对指标 | 平均差值 | 95% 自助法置信区间 | 序列胜 / 平 / 负 |
| --- | ---: | ---: | ---: |
| CARRY | **+0.041** | `[-0.083, +0.156]` | 6 / 2 / 4 |
| SUPPRESS | **−0.093** | `[-0.212, +0.009]` | 1 / 7 / 3 |

两个区间都跨过 0。样本支持的稳妥表述是：

- **MemTranslator 的观测强项是 CARRY**：多带入 5 个适用记忆，在 12 个序列中赢 6 个、输 4 个、平 2 个。
- **Codex 的观测强项是 SUPPRESS**：只泄漏 1/35，MemTranslator 泄漏 5/35；但多数交互序列没有差异，差距由 3 个序列驱动。
- **Task-perfect 表现接近**：66.0% vs 65.0%。当前 12 个簇的样本不足以建立总体统计优势。

## 5. 运行侧观测

MemTranslator 这轮的补充运行指标如下：

| 指标 | 数值 |
| --- | ---: |
| 每个交互序列的峰值活跃记忆数 | 29–42 |
| 每个探针的活跃记忆库文本长度，按序列取宏平均 | 2,345 字符 |
| 每个探针的 Translator 延迟，按序列取宏平均 | 11,225 ms |
| 未改写率，按序列取宏平均 | 7.1% |
| CARRY 评判器解析异常标记 | 0 |

Codex 报告给出的运行元数据为：209 次记忆维护调用、103 次计分读出、2,082,725 个报告的 token、15,179,459 ms 的累计调用延迟，以及计分读出时平均 4,470.6 个字符的冻结记忆文件。

这些数字**不能直接用于速度或成本排名**：MemTranslator 快照没有记录完整写入器和提取器的 token 用量与调用成本，且其 11.2 秒是 Translator 在探针上的延迟；Codex 的 15.18M ms 则合并了维护和读出调用。
两边的字符数指标也分别对应活跃记忆库文本和完整冻结文件，只能用于说明各自的运行规模。

## 6. 结论与下一步

当前 E1 含噪声场景结果给 MemTranslator 的定位很清楚：

1. **产品能力已经成立，但远未饱和。** 在 6,225 轮含噪声历史上，69.2% 的适用记忆被正确带入，66.0% 的任务全部正确。
2. **相对 Codex，MemTranslator 更偏“记得并用上”。** CARRY 多命中 5/107，尤其在 `e-03`、`e-12` 有明显优势。
3. **Codex 更偏“宁缺毋滥”。** 它在 SUPPRESS 上只泄漏 1/35；MemTranslator 的 5 次泄漏集中在 `e-01`、`e-04`、`e-06`，适合做定向的生命周期错误分析。
4. **内部状态仍是核心改进方向。** STATE 约 0.707，说明记忆库缺失活跃记忆或残留失效记忆的问题尚未解决。读取路径优化不能替代写入和生命周期管理的修复。
5. **当前总体胜负未定。** 配对置信区间均跨过 0，Task-perfect 只差 1/103。下一轮应增加重复运行或交互序列簇，并固定同一个读出模型来分析写入和检索的贡献，避免把模型能力差异误归因于记忆架构。

优先建议按以下顺序继续：

1. 对 `e-01`、`e-04`、`e-06` 的 5 个 SUPPRESS 泄漏逐项追踪归因，分成写入阶段未淘汰、检索越界、Translator 忽略状态三类。
2. 对 `e-01`、`e-04`、`e-09` 的 CARRY 未命中项，记录标准要求是否进入记忆库、召回候选、提示词，以及是否被 Translator 采用，形成四阶段漏失分析。
3. 在同一指标版本上做至少 3 次完整复跑，报告配对运行结果的分布，而不是用单轮模型波动裁决小于 5 个百分点的差异。
4. 补齐端到端 token 用量、调用数和实际经过时间的记录后，再与 Codex 做成本与效果比较。

## 7. 限制与数据来源

- E1 只有 12 个交互序列簇，置信区间仍较宽；单轮结果不适合裁决小差距。
- CARRY 使用评判器评分；本轮解析异常标记为 0，但评判器仍可能存在系统性偏差。
- 本比较针对两套原生完整系统，不隔离记忆写入器、检索器或读出模型的单独贡献。
- Codex 没有与 MemTranslator Store 等价的结构化状态，因此不报告或推断 Codex STATE。
- MemTranslator 的 12 份 metric-v12 机器快照已在原报告编写时的工作区中核验；这些运行产物生成在被 Git 忽略的 `bench/results/`，不作为源码长期保存。Codex 的逐序列与汇总数字来自用户提供的 `2026-08-25-codex-vs-memtranslator-e1.md`。其中提到的正式 Codex 快照不在原报告编写时的工作区，故原报告未独立重放 Codex 原始检查点。
- 旧版 E1 分数日志使用不同子集、指标版本和配置，不应与本轮含噪声场景的整组结果直接串成趋势线。
