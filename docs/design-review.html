信号机制设计评审：体验与性能的每一笔交易

对两条 memory 信号路（对话流批提取 · 编辑 diff 归因）与读路径的逐项决策复盘：每个设计的备选、优缺点、以及为什么最终选它。两轮评审累计修正七处（M1–M4 自查；M5–M7 来自 2026-07-23 反馈：长输入预筛、scope/key 结构化、单一后端）。红线不变：单轮全部 LLM 调用 < 10k tokens；用户可感知的等待只允许出现在一处。

§3十个决策，逐个交代

每张卡：备选方案 → 体验/性能两栏的优缺点 → 为什么选它。

D1

读路径召回：requirement 怎么进 translator

全量注入 · cap 32

体验轴 = 该触发的 requirement 不许漏；性能轴 = 热键轮的 token 与延迟。

全量注入活跃条目按新近取 ≤32 条
零漏召回——scope 判定全权交给模型，改写质量只取决于 translator 本身；无 embedding 基建
store 长大后线性涨 token；>100 条时注意力稀释、误应用率会抬头
embedding top-k
token 恒定，规模无关
召回失败 = 该改的没改，用户面前直接漏（体验硬伤）；多一层基建与调参
LLM 先选后用
召回准
热键轮 +1 次串行调用，等待时间近乎翻倍——伤在唯一的前台环节上

为何个人 requirement 库的真实量级是几十条不是几千条（它只记「任务怎么交付」，不记事实）。在这个量级，漏召回的体验代价远大于 ~700 token 的性能代价。M6 后升级路径也变了：先走 scope 确定性过滤（app/task 匹配当前上下文，0 LLM）＋ key 词面排序，embedding 排最后——结构化路径先于向量。

D2

热键改写：一次调用还是两级生成

单 flash call

这是全系统唯一的前台等待，1 秒的差别用户全额感知。

单次 haiku call
1–2s 出结果（Typeless 已验证此档体感成立）；实现最薄；错了有人在环兜底
长文本重写的精细度有限；风格控制全押在 prompt + style guide 上
两级：即时 patch + 终稿重写Typeless V2.0 的形态
长输入下保真与重组质量更高
延迟翻倍或需流式灰显基建；v0 的请求长度（聊天框一段话）用不出优势
本地小模型
离线、零 API 成本、隐私叙事满分
改写质量断崖；用户装机成本（下载 GB 级权重）直接劝退开源用户

为何anchor §5 把「热键体感」定为第一优先级，而 v0 的输入都是短请求——两级生成的收益在这个场景为零，却把唯一的前台延迟翻倍。两级留作 v2（anchor §7 原文如此）。

D3

路 A 提取的触发时机

batch N=8 + 空闲 30min 冲刷

学习的及时性（体验） vs 调用频率与信噪比（性能）。

per-turn 即时提取
纠正立刻生效，「越用越懂」的反馈最快
每轮 +1 call（多数轮空转）；单轮信噪比最低，重复/矛盾条目最多，后续 consolidation 负担成倍
batch 5–10 轮已拍板：默认 8
调用摊薄 8×；批内上下文让「反复强调」这类跨轮信号可见（单轮提取根本看不见它）
学习滞后最多 8 轮——刚立的规矩下一句还不生效（用 M3 的高置信旁路缓解）
session 结束时
调用最少，上下文最全
agent 场景 session 可以一天不结束；hook 侧「session 边界」信号并不可靠

为何「反复强调」是 requirement 的一等证据（anchor §2.1），它只在批视野里可见——batch 不只是省钱，是提取质量的需要。滞后的体验代价由 M3 的显式立规旁路补上。

D4

预筛：哪些内容值得进提取批（M5 修订）

句级候选定位 · 传统 NLP · 0 LLM

省掉无信号批的整次调用 vs 别漏信号——尤其用户把整份文档粘进输入框、requirement 只是其中一句的场景。

轮级句式表初版方案，已废
零成本，实现十行
轮级二分类 + 整轮截断 300t：长输入里的信号句直接被截丢；委婉纠正整轮漏掉——recall 在真实输入分布下不成立
句级候选定位分块 → 句级特征打分 → span 提交
仍 0 LLM；材料区（粘贴的文档/代码/引用）被识别后永不进提取 prompt，信号句带 ±1 句窗提交（单轮 ≤600t）——长输入下 recall 与成本同时成立
特征工程要维护（纠正/立规词表、meta-discourse 领域词、祈使句式、二人称指涉、首尾位置、与已有 key 的词面命中）；打分阈值需要 events 数据校准
LLM 微调用筛选
召回最全，长输入也能读懂
「为了省一次 call 先花一次 call」——预筛的存在意义被自己抵消

为何轮级门在「文档粘贴」输入分布下失效是硬伤（信号在轮内的位置不确定，截断即丢失）。句级定位把预筛从二分类升级为定位器：材料区剔除解决长输入，多特征打分把 recall 边界从「句式没命中」缩到「全部特征不命中」，且保住整批无信号 = 0 call 的账本性质。可选增强：本地小 embedding 对原型句做相似度（不引重依赖，先不上）。

D5

新旧记忆的关系判定（new / reinforce / contradict）

facet key 分桶 + 内嵌判定（M6 修订）

Mem0 的教科书做法是 per-fact 一次 update call——精度好，账单也好看不了。M6 修订后：每条 requirement 带 key: "facet.attribute"（如 email.length）与 scope: {app, task, lang}，候选先按 key 分桶，同桶才需要判定——HMS 的 SAME FACET 纪律从 prompt 文字变成数据结构（借 SimpleMem 符号层）。

Mem0 式 per-fact call
每条新事实独立对照 top-s 相似旧记忆，判定最准
一批 5 条候选 = +5 次调用；token 翻倍还引入串行延迟链
内嵌判定全库一行索引已在提取 prompt 里
零额外调用——判关系所需的「旧记忆视野」本来就为提取注入了，复用它
索引只有一行摘要，语义边界模糊的对（0.55–0.8 相似区）判不准
全推给低频 consolidation
写入路径最快
重复条目在库里存活数天，读路径注入重复内容，改写行为肉眼可见地抽风

为何key 桶命中时判定几乎免费且不会跨 facet 误合并；内嵌覆盖清晰判定；只有「同桶且语义边界模糊」的残余灰区才走一跳 Mandol 式 match-judge（编号候选 + confidence≥0.7 + 向量兜底）——按需付费，而不是 per-fact 固定付费。key 由提取 call 顺带输出（受控两段式词表引导 + 允许新造），不加调用。

D6

噪声闸门：什么才配入库

salience 打分内嵌提取输出

库的纯度直接决定改写质量——每条噪声都会在未来某次热键时当面出丑。

提取时顺带打分salience 1–5，<3 丢弃
零额外调用（多两个输出 token）；借 Generative Agents 的 importance 思路，闸门在入口
单次打分有方差；边界分（3）的条目质量不稳
全收，事后 consolidation 清理
不会错杀
脏库先跑几天再洗——用户先看到错误改写，再看到它被修正，信任已经掉了

为何信任只有一次建立机会（false application 是诊断阶段就定性的头号风险）。宁可错杀低分候选——真 requirement 会再来，strength 机制会把它捞回来。

D7

diff 归因：机械层和 LLM 层怎么分工

机械保守判定 + LLM 批量定性

diff 事件天然稀疏，但每一个都是高价值信号——不能丢，也不值得逐个花钱。

全 LLM 逐个归因
语义判断最准，能读出「删掉约束是因为这次是特例」
每个 diff 一次调用；多数 diff 只是小改，杀鸡用牛刀
两层span 重叠免费初判 → 攒 5 个批量定性
strength 的±1 即时发生（0 token）；LLM 只花在需要语义的四分类上，且搭路 A 的批
两层间要维护「待定性」队列；机械层在中文/重排下有误判风险（见 M1 的保守化修正）
全机械
零成本
分不出「requirement 错了」和「改写风格错了」——路 B 一半的价值（style 信号）直接消失

为何misapplied 与 style 的区分必须语义层做（它决定信号进哪个库），但 kept/removed 的粗判 span 重叠就够。让免费层跑在前面、LLM 层攒批殿后，是这条路上唯一同时保住两轴的分工。

D8

style 信号往哪放：b2 类 diff 的归宿（M7 修订）

同一后端 · kind: style_rule

b2 类 diff（约束保留、措辞被改）指向 translator 自己的毛病——这类信号必须有归宿，但不能为它另立存储。

同库的 style_rule 条目kind 字段区分，Dynamic Cheatsheet 式策展
单一 memory 后端：同一 JSONL、同一状态机、同一管理页与退役机制全部复用；语义边界靠 kind 保持（requirement 管任务怎么交付，style_rule 管改写怎么做）；≤10 条 ≤250 token 上限锁死成本
热键轮 +~250 token；kind 混排要求管理页分组展示，检索层要排除 style_rule
独立旁库初版方案，已废
检索/注入路径天然隔离
违反「只有一个 memory 后端」：双份存储、双份状态机、双份管理面——diff 应是改进唯一 memory 的机制，不是第二套系统的入口
不做b2 信号丢弃
系统最简
路 B 半条腿消失——「改进改写机制」失去数据载体

为何信号要收、后端要唯一，两个都不让步的解就是 kind 内分。style_rule 不参与 scope 检索、只在改写 prompt 组装时注入，行为上与旁库等价，架构上零新增。

D9

入库策略：自动还是人工批准

自动入库 + 显眼可退役

Cursor Memories 用「sidecar 提议 + 人工批准」，2.1.x 整个功能被砍——前车之鉴就摆在那。

自动入库面板高亮新条目，一键退役/编辑
零打扰，「越来越懂我」自己发生；错误条目的代价被人在环兜底（改写永远可编辑可还原）
错误提取会短暂生效直到被退役；用户对「它记了什么」需要事后而非事前控制
提议 + 批准Cursor Memories 路线
库的纯度上限最高，用户全程知情
每条记忆一次打断；批准疲劳 → 全点掉或全忽略，功能名存实亡——Cursor 已替我们付费验证了这条路的终点

为何我们的信号密度（行为 diff、重复纠正）远高于 Cursor 从闲聊里猜——自动入库的错误率起点就低；且产品有双保险：改写本身人在环、条目本身可见可退役。打扰换纯度这笔交易，在我们的信号质量下不划算。

D10

两通道的 join：怎么认出「这条 submit 源自那次改写」

时间窗 + 相似度 · 不埋标记

join 错了会污染 strength 与归因——但为了 join 准而弄脏下游输入是本末倒置。

时间窗 15min + 文本相似度
下游输入绝对干净；daemon 两侧事件都在手，无需任何协作方配合
模糊匹配有错判率（阈值 0.55/0.85 是初值）——由 M2 把 strength 更新与模糊 join 解耦来兜底
文本内埋隐形标记
join 100% 准
标记会随文本进下游模型——污染 agent 输入，违反「下游只见确认文本」的产品契约，泄露 MemTranslator 的存在
hook 侧传 translate_id
又准又干净
做不到：hook 只能看到 agent 输入框里的文本，而写回发生在 AX 层，两者之间没有可携带元数据的通道

为何三选一里只有它同时满足「输入纯净」这条不可让步的产品契约和技术可行性。错判率用架构手段(M2)隔离，再用 events 数据校准阈值——而不是用弄脏文本来解决。

§4两轮评审改掉的七处

Review 的产出不只是解释，还有修正——以下与原提案不同，以本页为准。M1–M4 来自自查，M5–M7 来自 2026-07-23 的反馈轮。

M1机械 span 层降级为「保守判定」

原提案让 B1 机械层判 kept / touched / removed 并直接驱动 strength。问题：中文字符级 diff 加上改写重排，span 重叠的误判率不可忽视。修正：只有「注入 span 完全消失」才判 removed，其余一律标 touched 交给 B2 的 LLM 定性——免费层只做它错不了的部分。

M2strength 更新与模糊 join 解耦

原提案里 fuzzy join（相似度 0.55–0.85）的结果同样触发 strength±1。问题：join 错判会静默污染 requirement 的生死簿。修正：strength 只由高置信信号驱动——exact match 的 accepted_verbatim、B1 的保守 removed、B2 的显式 verdict；模糊 join 只做归档与统计，不动库。

M3给「显式立规」开即时旁路（可选，默认关）

batch=8 的学习滞后有一个刺眼的场景：用户刚说「以后都用英文写 commit」，下一条还是中文——立规这件事的反馈期望是即时的。修正：natural 消息命中强立规句式（「以后都 / 记住 / 从现在起」）时允许单条即时提取（+1 次 call，频率极低）。作为可调项交给拍板，不改默认。

M4join 只读事件尾窗

当前实现每次 submit 读全量 events 再过滤（O(n) 随月份增长）。修正：join 只需要 15 分钟窗口，读文件尾部即可；events 按月分段留给 v1。纯工程项，不影响机制。

M5预筛从轮级句式表升级为句级候选定位（改 D4）

rule-based 轮级门在长输入下不成立：用户把整份文档粘进输入框、requirement 只是其中一句时，轮级截断直接把信号截丢。修正：传统 NLP 三步——分块识别材料区（永不进 prompt）→ 句级多特征打分 → top-k 信号句带 ±1 句窗提交（单轮 ≤600t）。0 LLM 与「无信号批 = 0 call」的性质都保留。

M6schema 升级：每条 requirement 配 scope 与 facet key（改 D5/D1，借 SimpleMem）

SimpleMem（arXiv 2601.02553）的符号索引层证明结构化属性可以承担确定性过滤。修正：每条带 key: "facet.attribute" 与 scope: {app, task, lang}，提取 call 顺带输出——consolidation 按 key 分桶（SAME FACET 从 prompt 纪律变成数据结构），读路径按 scope 过滤（0 LLM）。不搬它的三层索引与 per-query 检索规划：热键轮零额外调用是红线。

M7单一 memory 后端：style guide 旁库收编为 kind（改 D8/D10）

自查确认：路 A / 路 B 在原提案中已汇入同一 requirement store，但 style guide 确实立了第二个存储——违反「只有一个 memory 后端」。修正：style rule 成为同库的 kind: style_rule 条目，同一 JSONL、状态机、管理页、退役机制；不参与 scope 检索，仅在改写 prompt 组装时注入。diff 自始至终只是改进唯一 memory 的机制，不是存储。
