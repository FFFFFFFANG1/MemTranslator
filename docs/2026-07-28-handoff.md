## 2. 六桶到底伤在哪（已定位，有 A/B）

`da52a7d` 给 extraction prompt 加了 4a(ATOMISE) 和 4b(BUCKET)。副作用是模型开始把**实例写进规则文本**：

```
六桶前：邮件不超过120词。            ← 类别
六桶后：给房东的邮件不超过120词。      ← 实例，下一轮收件人一换就永不触发
```

`bench/gen/probes/scope_ab.py` 在 writer-zh 的首次 flush 上跑 20 次：写窄的 trial 从 **0/20 涨到 19/20**。
后续轮次收件人一变，translate 的 no-op bias 正确地判定规则不适用 → persona 全程学不会 → E 塌。

4c 就是为此加的（"STATE THE CLASS, NOT THE INSTANCE"）。长版把写窄压到 1/20，但把
minimalist-zh 从 0.708 打到 0.194——那个 persona 的三条规则（回答短、别用 bullet、别复述问题）
是全局的，没有类别可写，"剥掉收件人/文件名"这类祈使对它是毒药。精简版（当前工作区，未提交）
把 minimalist 救回 0.875，代价是写窄只压到 8/20，writer 退到 0.528。

**结论：4c 两个版本都不对。**问题不在措辞长短，在于它想用一条通用指令同时管住"该收窄的别收窄"
和"本来就全局的别硬找类别"，而这两件事的正确行为相反。真要修得让规则文本的粒度跟着用户实际
说话的粒度走，而那正是 `scope` 字段该干的活，现在两版都在往 `text` 里挤。

**但这个判断先别急着动手验。** 8 persona、一个翻转就是 ±0.1、repeat 内极差 0.58 的尺子，
量不出这个粒度的改动。先把新 E 建起来。

## 5. 顺带挖出的四个产品/harness 真 bug（都已核实，未修）

1. `consolidate.should_consolidate` 是 `active > 48 **或** adds >= 16`——
   `CONSOLIDATE_ADDS=16` 必然先命中并重置计数，**`CONSOLIDATE_ACTIVE=48` 这条分支实践中永不触发**
2. `Pipeline.maybe_flush` 不调用 consolidation
3. persona 文件存了 `final` 字段——把 SUT 的输出当成常量写死进了 case
4. `run_e2e.py:86` 只把 `task` 喂 translate，而真实使用里最高频的形态是
   "请求和规则在同一句话里"（carrier 轮），从未被测过

另外两条已核实的产品事实，决定了新 E 能声称什么：

- `signals._KEY_LEXICON` 只有 14 个词根，`recall()` 在 pool=52 时输出与"取最新 32 条"重合 30/32。
  **不能声称检索精度好**
- `translate._requirement_block` 只打印 `- [id] text`，**scope 字段从不进 prompt**。
  **不能声称 scope 过滤有效**

## 6. 换机器要注意的环境事项

- `ANTHROPIC_API_KEY` **不在 Bash 工具子进程的环境里**（`~/.zshrc` 有无条件 export，但没传进来）。
  每条要发 Anthropic 请求的命令前面加 `eval "$(grep '^export ANTHROPIC_API_KEY=' ~/.zshrc)"`，
  否则报 `TypeError: Could not resolve authentication method`（不是余额问题）
- 两条通道互相独立：产品路径（translate/extraction）走 `claude-haiku-4-5` on Anthropic；
  bench 的 judge 与造数走 repo 根 `.env` 里的 Ark/DeepSeek。`.env` 里的 `LLM_MODEL` 没有任何代码读取

- iCloud 目录里的 `.venv` 会被同步搞坏，现在是符号链接指向 `~/.venvs/memtranslator-venv`，
  换机器要重建：`uv sync`
- 一次完整 gate 跑（T+L+E）约 $1.7、40 分钟，4 workers 稳定
